# 영업관리 운영 안내 (역할 · 서비스 수준 · 감시 · 정기 점검 · 변경 관리)

장애가 났을 때의 절차는 [RUNBOOK.md](RUNBOOK.md), 보안 통제는 [SECURITY.md](SECURITY.md)를 본다. 이 문서는 **누가 무엇을 맡고, 얼마나 빨리
고치고, 평소에 무엇을 확인하며, 어떻게 바꾸는지**를 정한다. 값은 초안이며 회사와 계약(또는 내규)에서 확정한다.

## 1. 역할과 연락

| 역할 | 맡는 일 | 연락(회사에서 채움) |
|---|---|---|
| 서비스 책임자 | 우선순위·예산·장애 등급 판단, 외부(ERP·ASP·IdP) 협의 | |
| 운영 담당(전산) | 서버·DB·백업·배포, 경보 대응, `manage.py doctor` | |
| 데이터 관리자(영업지원 SUPPORT) | 데이터 점검·거래처 병합·품목·엑셀 일괄 등록, 현업 문의 1차 | |
| 시스템관리자(ADMIN) | 사용자·권한·회사 설정, 월 마감, 감사로그, 증빙 무효 요청 검토 | |
| 재무·세무 담당 | 세금계산서·대손·월 마감 확인, 홈택스 대사 | |
| 보안 담당 | 감사로그 이상 행위, 접근 권한 분기 검토, 사고 대응 | |

사용자 문의는 화면 오류 문구의 **문의 번호**(요청 ID)를 받아 감사로그 상세 검색(`/admin/audit` > 상세 검색)에 넣으면 그 요청이 한 줄로 이어진다.

## 3. 감시

- `/healthz`(살아 있음) · `/readyz`(DB·스키마·저장소 준비) · `/metrics`(Prometheus, `SALES_METRICS_TOKEN`) · 경보 규칙 `deploy/alerts.yml`
- 매일: 관리자 > ⏱️ 배치 작업 > 🩺 운영 점검(또는 `python manage.py doctor` 종료 코드) — 백업 최근성·같은 디스크·**증빙 파일 백업 누락**·워커·ERP 실패·저장소
- 매일: 관리자 > 🩺 데이터 점검 — 높음 항목 0건 유지(입금액≠입금내역, 수주 초과 납품 등), 결재 기한 넘김·세금계산서 없는 지난달 매출
- 로그: `SALES_LOG_JSON=1` 이면 JSON 한 줄(요청 ID 포함). 감사로그는 `SALES_AUDIT_STDOUT=1` 로 표준출력에도 남길 수 있다.

## 4. 백업과 복구 시험

- DB: 매일 02:00 작업 `backup.db`(검사 통과한 사본만 보관, 일·월말·연말 세대). PostgreSQL 은 `pg_dump` + `pg_restore --list` 검증.
- **증빙·첨부 파일**: DB 백업과 같은 폴더의 `files/` 로 새 파일만 복사하고 `files.json` 에 sha256 을 남긴다(변조된 파일은 덮어쓰지 않음).
  **DB 백업만으로는 세금계산서 이미지·XML·첨부가 복원되지 않는다** — 백업 폴더 전체를 다른 디스크·NAS 로 복사한다.
  관리자 > 데이터 관리 > '증빙·첨부 파일 zip' 으로 따로 받을 수도 있다.
- 복구 순서: ① 점검 모드 켜기 ② `python manage.py restore <DB 백업 파일> --yes`(복구 전 현재 DB 를 한 번 더 백업) ③ `python manage.py restore-files <백업 폴더>`
  (저장소에 없는 파일만 되돌리고 sha256 확인) ④ `python manage.py db upgrade` ⑤ `doctor` ⑥ 점검 모드 끄기.
- **분기마다 복구 시험**: 새 서버(또는 임시 DB)에 위 순서로 복구 → 로그인·매출 화면·증빙 열람(원본 있음)·감사로그 무결성 검증 → 걸린 시간을 기록(RTO 확인).

## 5. 정기 점검

| 주기 | 점검 |
|---|---|
| 매일 | 감시 경보, ERP 전송 실패 0건, 세금계산서 발행 '진행 중' 장기 체류 없음, 워커 정상, 결재 기한 넘김 |
| 매주 | 거래처 '이름 정리' 미등록 이름, 알림 실패, 홈택스 대사(매출 전자세금계산서 목록) |
| 매월 | **월 마감**(마감 전 점검 → 마감), 거래처별 채권 ERP 대사, 사용자·권한·데이터 범위 예외(기한 지난 것) 검토, 감사로그 이상 행위, 증빙 무효 처리 내역 |
| 분기 | 백업 복구 시험, 의존성 취약점 점검(`pip-audit`, 이 저장소 CI 에서 자동), 보안 점검 문서 갱신, 접근 권한 재확인 |
| 연 1회 | 외부 모의해킹(권고), 장애 대응 훈련, 대손·세금계산서 처리 규칙 세무 검토 |

## 6. 변경 관리 (배포)

1. 변경은 브랜치에서 테스트 통과(CI: SQLite·PostgreSQL·보안 검사) 후 병합한다.
2. DB 구조 변경은 리비전 파일로만(`migrations/versions/00NN_*.py`, 확장 → 전환 → 축소). 같은 번호가 겹치지 않게 최신 리비전을 확인한다.
3. 배포 전 **백업** → 배포(시작 때 최신 리비전까지 자동 적용되는 환경은 그 로그 확인) → `/readyz` · `doctor` · 주요 화면(대시보드·매출·결재함) 확인.
4. 배포 기록: 날짜·커밋·변경 요약·담당자를 남긴다(이 저장소는 커밋 이력으로 대신하고, 운영 환경은 별도 대장).
5. 문제가 있으면 이전 버전으로 되돌린다. 스키마는 되돌리지 않는 것이 원칙이며 꼭 필요하면 `python manage.py db downgrade <리비전> --yes`(자동 백업 후).
6. 긴급 수정(보안·데이터 손상)은 절차를 줄이되 사후에 사유와 영향을 기록한다.

## 7. 초기 설치 (최초 1회)

1. 환경변수 설정(`SALES_ENV=production`, `SALES_SECRET_KEY`, DB 주소, 로그인 방식 등 — SECURITY.md 3절) → `python manage.py db upgrade`
2. 사용자가 0명이면 `/setup` 이 열린다. **서버 콘솔(로그)에 `[초기 설정] … 코드` 가 찍히고, 그 코드를 입력해야 관리자가 만들어진다**
   (서버가 여러 대면 `SALES_SETUP_CODE` 로 같은 값을 정해 둔다). 관리자가 생기면 코드는 폐기되고 `/setup` 은 로그인으로 돌아간다.
3. 관리자로 로그인해 회사 설정·조직·사용자·ERP·알림 채널을 채우고 `doctor` 로 확인한다.
