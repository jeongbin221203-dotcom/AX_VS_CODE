# 자재관리 운영 안내 (유지보수 · 장애 대응 · 감시)

이 문서는 회사에서 이 프로그램을 실제로 쓸 때 **누가, 언제까지, 무엇을** 하는지 정하는 틀이다.
빈칸(＿＿)은 도입하는 회사가 채운다. 지금은 한 사람이 만든 프로그램이므로, **아래 표를 채우고 인수인계를 마치기 전에는 운영 시스템으로 쓰지 않는다.**

## 1. 역할과 연락

| 역할 | 하는 일 | 담당 | 연락 |
|---|---|---|---|
| 업무 책임자 (자재·구매 팀장) | 업무 규칙·결재 기준 결정, 월 마감 승인, 장애 때 업무 대체 방법 결정 | ＿＿ | ＿＿ |
| 시스템 담당 (사내 IT) | 서버·DB·백업·계정·권한, 감시 알림 받기, 1차 장애 대응 | ＿＿ | ＿＿ |
| 유지보수 (개발) | 오류 수정, 기능 변경, DB 구조 변경(리비전), 보안 패치 | ＿＿ | ＿＿ |
| ERP 담당 | SAP·ERP 연결 계정·인증서, 전송 실패 원인 확인 | ＿＿ | ＿＿ |

## 2. 서비스 수준 목표 (초안 — 계약 때 확정)

| 항목 | 목표 |
|---|---|
| 서비스 시간 | 평일 07:00~22:00 (야간·주말은 최선 대응) |
| 가용성 | 서비스 시간 기준 월 99.5% (약 3시간 40분 이하 중단) |
| 데이터 손실 한도 (RPO) | 마지막 백업 이후 — 기본 6시간마다 백업(`MM_BACKUP_HOURS`). PostgreSQL WAL 보관을 쓰면 수 분 |
| 복구 시간 (RTO) | 4시간 이내 (백업에서 새 서버로 복구 기준) |
| 현장 업무 지속 | 서버가 멈춰도 입출고 화면은 브라우저 대기열로 계속 입력, 연결되면 반영 (같은 규칙으로 다시 판정) |

### 장애 등급

| 등급 | 예 | 첫 대응 | 복구 목표 |
|---|---|---|---|
| P1 | 앱·DB 전체 중단, 데이터 손상 의심 | 15분 | 4시간 |
| P2 | ERP 전송 실패 누적, 배치(백업·전송·알림) 멈춤, 서버 오류 5% 넘음 | 1시간 (업무 시간) | 다음 업무일 |
| P3 | 느린 화면, 알림 실패, 일부 기능 오류 | 다음 업무일 | 1주 |
| P4 | 개선 요청 | 정기 회의 | 일정 협의 |

감시 알림 규칙(`deploy/prometheus/alerts.yml`)의 `severity` 가 이 등급과 같다.

## 3. 감시

- `GET /health` — 로드밸런서용 (DB·파일 저장소). 로그인 없이 열리고 내부 정보는 없다.
- `GET /readyz` — 배포 뒤 '받을 준비 됨': DB 연결 + DB 구조가 최신 리비전(아니면 503). 점검 모드인지도 알려 준다.
- 요청 번호: 응답 헤더 `X-Request-ID`, 오류 화면의 '문의 번호'. `MM_LOG_JSON=1` 이면 로그 한 줄마다 JSON(요청 번호·경로·사용자)으로 남아 로그 수집기에서 찾는다.
- 🩺 데이터 점검(관리자 메뉴): 음수 재고·초과 입고·거래처 중복·BOM 문제 등 데이터 품질 — 매주 확인.
- `GET /metrics` — Prometheus 지표. `MM_METRICS_TOKEN` 을 정하고 Prometheus 에 같은 토큰을 준다(없으면 서버 자신만).
  - 요청 수·응답 시간(화면별), DB 연결, ERP 전송 대기·실패, 결재 대기, 알림 실패, 재공품 금액, 안전재고 미달, 배치마다 마지막 성공 뒤 지난 시간.
- 설정 예: `deploy/prometheus/prometheus.yml`, 알림 규칙: `deploy/prometheus/alerts.yml` (Alertmanager → 메일·잔디·네이버웍스).
- `flask --app app doctor` — 실제 DB·저장소·ERP·SSO·백업·배치 연결을 한 번에 점검 (배치 화면의 '운영 점검' 버튼과 같음).

## 4. 장애 대응 절차

데이터를 멈춰야 하는 작업(DB 이전·복구·대량 정리) 전에는 **점검(읽기 전용) 모드**를 켠다: 관리자 → 🏢 회사 설정, 또는 `flask --app app read-only on --reason "..."`.

공통: ① 감시 알림·사용자 신고 확인 → ② 등급 정하고 업무 책임자에게 알림 → ③ 아래 절차 → ④ 복구 확인(`/health`, `doctor`) → ⑤ 장애 기록(원인·영향·재발 방지).

### 앱이 응답하지 않음
1. `/health` 확인. 응답이 없으면 앱 프로세스·서버 상태(메모리·디스크) 확인 후 재시작.
2. 여러 서버면 로드밸런서에서 빠졌는지 확인 — 다른 서버로 업무 계속.
3. 현장에는 "입출고 화면에서 계속 입력하면 대기열에 쌓였다가 반영됨"을 안내.

### DB 연결 실패
1. DB 서버·연결 수·디스크 확인. PostgreSQL 이면 `pg_isready`.
2. 데이터 손상이 의심되면 **쓰기를 막고**(앱 중지) 마지막 백업과 비교 — 백업 복구는 업무 책임자 승인 후.

### ERP 전송 실패
1. ERP·SAP 연동 화면에서 실패 사유 확인 (자재·창고 매핑, 원가센터, 인증).
2. 원인을 고친 뒤 '재전송'. 앱 재고는 이미 반영돼 있으므로 ERP 와의 차이는 '재고 대사' 화면으로 확인.

### 배치가 멈춤
1. 배치 화면에서 작업별 마지막 실행·오류 확인. 잠금이 남았으면 임대 시간(`JOB_LEASE_SECONDS`, 5분) 뒤 다른 서버가 이어받는다.
2. 배치 실행기(`flask --app app batch --loop`)가 떠 있는지 확인.

### 인터넷·서버가 끊긴 현장
- 입출고·이동·여러 줄 화면은 브라우저 대기열에 쌓는다. 연결되면 자동으로 보내고, 재고 부족 등으로 거부된 건은 사유와 함께 남는다 — 현장 담당자가 확인.

### 잘못 등록한 거래
- 삭제하지 않는다. 거래 이력에서 '취소'(다른 관리자) → 취소 거래가 남는다. 묶음·생산은 전체 취소. 마감된 달은 마감 해제(관리자) 후.

### 사내 로그인(SSO) 장애
- `flask --app app sso-outage --hours 4` (또는 사용자 화면) → 비밀번호 계정 로그인을 정해진 시간만 허용.

## 5. 백업과 복구 시험

- SQLite: 배치 `db_backup` 이 `MM_BACKUP_HOURS` 마다 검사 통과한 사본만 보관(일·월말 세대). **다른 디스크·다른 서버로 복사**(같은 디스크면 경고).
- PostgreSQL: `MM_PG_DUMP` 로 pg_dump, `pg_restore --list` 로 검사.
- **분기마다 복구 시험**: 백업을 새 DB로 복구 → 앱을 그 DB로 띄워 `doctor` · 재고 현황 · 감사로그 확인 → 걸린 시간을 기록(RTO 확인).

## 6. 정기 점검

| 주기 | 점검 |
|---|---|
| 매일 | 감시 알림, ERP 전송 실패 0건, 배치 정상, 결재 대기 오래된 건 |
| 매주 | 오프라인 대기열 거부 건, 거래처 '미등록 이름' 정리, 알림 실패 |
| 매월 | 월 마감, 재고 대사(ERP), 사용자·권한·창고 범위 검토(퇴사·이동), 감사로그 이상 행위 |
| 분기 | 백업 복구 시험, 의존성 취약점 점검(`pip-audit`), 보안 점검(docs/SECURITY.md) 갱신 |
| 연 1회 | 외부 모의해킹(권고), 장애 대응 훈련 |

## 7. 변경 관리 (배포)

1. 변경은 브랜치에서 테스트 통과(CI: SQLite·PostgreSQL·보안 검사) 후.
2. DB 구조 변경은 리비전 파일로만: `flask --app app db revision -m "설명"` → `upgrade`/`downgrade` 작성 → 테스트.
3. 배포 전 백업 → 배포(앱이 뜰 때 최신 리비전까지 자동으로 올림) → `/health`·`doctor`·주요 화면 확인.
4. 문제가 있으면 이전 버전으로 되돌리고 `flask --app app db downgrade <리비전> --yes` (먼저 백업).
