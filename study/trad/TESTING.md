## 서버 점검 (2026-10-10)

실제 서버 프로세스와 테스트 클라이언트로 이상한 요청을 대량으로 보내 오류를 찾았습니다(경로×메서드 전수, 본문 퍼징 100여 종, 크기 한계, OpenAI 호출 실패 11종·응답 몸통 10종, 경로 탈출·정보 노출 20여 곳, 보안 헤더, Host 헤더, PDF Range, 동시 접속·메모리).

**찾아서 고친 것**

1. **`/api/convert-backup`이 위장한 뷰를 읽어 서버를 붙잡을 수 있었음(심각)** — 올린 SQLite 파일의 "표"를 무조건 읽었는데, 파일 안에 계산식을 넣은 뷰를 표처럼 꾸미면 4KB 파일로 300만 행을 7.9초 동안 처리했고, 제한 없는 뷰는 끝나지 않거나 메모리를 소진함(로그인 없는 공개 서버). 진짜 표만 허용하고 행 수(시험 2,000·답 12만·메모/해설 840)와 처리 시간(10초) 한도를 둠 → 같은 파일이 0.0초에 거부됨. 수정 전 코드로 새 시험을 돌리면 이 시험이 끝나지 않고 멈춤.
2. 아주 큰 문제 번호(`/question-image/99999999999999999999/…`)가 500 → 404
3. OpenAI 연결 중 응답이 끊기는 오류(`IncompleteRead`·`BadStatusLine`)를 처리하지 않아 500 → 502 "AI 서버에 연결하지 못했습니다"
4. OpenAI 응답 모양이 이상할 때(`[]`·`null`·빈 내용 등 6종) 500 → 502
5. 규칙상 허용되는 긴 AI 대화(12개 × 한글 12,000자, 약 430KB)가 본문 한도 100KB에 걸려 영어 오류로 거부 → 한도를 1MB로 올림, 초과 시 한글 안내
6. 오류 문구가 영어("The data value transmitted exceeds…") → 한글로, 예상 밖 오류는 서버 내부 정보 없이 한글 JSON 500

**문제없음으로 확인한 것**: 모든 경로 × 7개 메서드에서 서버 오류 없음, 경로 탈출·소스·DB·`.git` 노출 없음(`/static/../app.py` 등), 모든 응답에 보안 헤더(CSP·nosniff·X-Frame-Options·Referrer-Policy), PDF Range 요청 206, Host 헤더 검증(`evil.example`·`localhost@evil.example` 등 거부), 이미지 60장 동시(30) 요청 2.2초·실패 0, 이미지 500장 반복 렌더링 후 메모리 75→88MB로 안정, 운영 로그에 서버 오류 없음.

**알려진 한계(고치지 않음)**: 로그인·요청 횟수 제한이 없어 누구나 AI 연결 확인(`/api/ai/settings`)을 통해 이 서버로 OpenAI 키를 시험해 볼 수 있음(서버는 키를 저장하지 않음), 이미지는 요청마다 새로 렌더링(브라우저가 하루 보관), `Host: LOCALHOST`(대문자)는 400(브라우저는 소문자로 보냄), 서버 시작 때 `fitz` 사용 중단 경고.

| 결과 화면에 `<h1>` 없음 | 페이지 제목 없음 | 결과 제목을 h1으로 |
| `<dialog aria-labelledby="dialog-title">`가 가리키는 대상이 처음에는 없음 | 잘못된 참조 | 열 때 붙이도록 변경 |
| `<button>` 18곳에 `type` 없음 | 폼 안으로 옮기면 의도치 않게 제출됨 | `type="button"` |
| JavaScript를 끄면 "준비하고 있어요…"만 영원히 보임 | 안내 없음 | `<noscript>` 안내로 교체 |
| 현재 메뉴 표시가 색뿐(`aria-current` 없음), `<meta name="description">` 없음 | 낭독기·검색 미리보기 | `aria-current="page"`, 설명 추가 |

수정 뒤 두 화면 크기 모두 **axe 위반 0건, 직접 점검 0건, 콘솔 오류 0건**이고, 기존 브라우저 흐름(웹 주소·`file://` 각 34/34)과 휴대폰 화면 12/12도 그대로 통과합니다. 재발 방지 시험을 추가했고, 네 가지를 일부러 되돌리면 시험이 실패하는 것을 확인했습니다.

**동작 점검 16/16**: 첫 Tab이 "본문으로 이동", Enter로 본문 포커스, 대화상자가 열리면 포커스가 안으로 들어가고 Esc로 닫으면 열었던 버튼으로 돌아옴, 숫자 키 1~4와 ←/→ 키, 입력 칸에 쓰는 중에는 숫자 키가 답 선택으로 가지 않음, `aria-pressed`·`aria-current`, 화면마다 문서 제목 변경, JavaScript 끔 안내, 320px 폭에서 가로 스크롤 없음.

**고치지 않은 것(알려진 한계)**: 사이트를 새로 올린 직후 브라우저가 이전 `app.js`·`catalog.js`를 잠시 보관하고 있으면 새 `index.html`과 섞일 수 있음(Render 정적 사이트는 항상 새로 확인해 문제없고, GitHub Pages는 약 10분). 이미지는 파일 이름이 내용 해시라 안전함. 어두운 테마(`prefers-color-scheme`)는 지원하지 않음.

## 어두운 테마 (2026-10-10)

HTML 버전(`../trad_study`)과 같은 화면 코드·스타일입니다. 스타일 생성기(`gen_dark_theme.py`)는 HTML 버전에만 있고, 이 버전의 `style.css`는 같은 결과를 복사한 것이므로 밝은 스타일을 고칠 때는 그쪽에서 생성해 두 파일에 반영하세요(테스트가 두 파일의 일치를 확인).

운영체제의 어두운 설정을 따르고, 위쪽의 `자동`/`다크`/`라이트` 버튼으로 직접 고를 수도 있습니다(누를 때마다 자동 → 다크 → 라이트 → 자동). 선택은 이 브라우저에 저장되고, 다음 방문 때 첫 화면이 그려지기 전에 적용되어 밝은 화면이 번쩍이지 않습니다.

- **방식**: CSS `light-dark(밝은색, 어두운색)`과 `color-scheme`. 밝은 테마 값은 그대로 두고 색이 든 규칙(149개)마다 어두운 색을 덧붙였습니다. 어두운 색은 밝은 색의 밝기를 뒤집어 계산하고(배경·테두리는 어둡게, 글자는 밝게, 초록 버튼처럼 이미 진한 색은 그대로) 순백·회색은 이 앱의 초록빛으로 물들였습니다. 문제 이미지는 시험지 원본 그대로 흰 바탕으로 둡니다.
- **만드는 법**: `python scripts/gen_dark_theme.py`가 `static/style.css` 끝의 표시된 구간을 다시 만듭니다(밝은 스타일을 고친 뒤에는 다시 실행, `--check`로 최신 여부 검사). 색이 든 선언은 값이 같아도 같은 순서로 내보내고 `border`·`background` 약식은 색 부분만 개별 속성으로 내보내, 스타일 우선순위가 바뀌지 않게 했습니다.
- **밝은 테마는 달라지지 않음**: 화면 13개의 모든 요소(약 2,000개)의 계산된 색(글자·배경·테두리 4면·윤곽선·그림자·강조색)을 생성 전후로 비교해 바뀐 요소 0개(새 전환 버튼 요소만 추가).
- **글자 대비**: 어두운 테마도 WCAG AA(4.5:1) 만족 — 화면 13개 × 데스크톱·휴대폰 × 밝음·어두움 4가지 조합 모두 axe 위반 0건, 구조 점검 0건, 콘솔 오류 0건. 만드는 중 찾은 문제: 색 이름 `white`(12곳)를 변환하지 않아 버튼 배경이 흰색으로 남던 것, 순서 때문에 번호판 현재 칸의 테두리색이 달라지던 것(밝은 테마에서 발견), 포커스 링이 어두운 배경에서 안 보이게 뒤집히던 것 → 모두 고침.
- **동작 19/19**(헤드리스 Chrome): 처음엔 운영체제 설정을 따름, 누를 때마다 라벨·`aria-label`·저장값이 바뀜, 새로 고침 뒤에도 유지, **첫 그림이 그려질 때 이미 선택한 테마**, 라이트를 골라 두면 운영체제가 어두워도 밝음, 자동으로 돌아오면 저장값 삭제 후 운영체제 변경(밝음↔어두움)을 실시간으로 따라감, 키보드(Enter) 전환, 어두운 화면에서 시험·문제 이미지 정상, 입력 칸도 어두운 색 구성, 390px·320px 상단 줄 넘침 없음(320px 이하에서는 라벨을 숨기고 아이콘만).
- **지원 범위**: `light-dark()`를 아는 브라우저(Chrome·Edge 123+, Firefox 120+, Safari 17.5+). 모르는 브라우저는 `@supports`로 걸러 어두운 테마만 빠지고 밝은 테마는 그대로 보입니다. 이번 점검은 Chrome 154에서만 했습니다.
