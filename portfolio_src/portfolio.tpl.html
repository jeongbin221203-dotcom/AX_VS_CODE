권한은 화면이 아니라 쿼리에서 막습니다

메뉴를 숨기는 것만으로는 데이터가 새어 나갈 수 있습니다. 로그인한 사용자가 볼 수 있는 담당자 id를 ContextVar에 담아, 모든 조회 쿼리에 조건이 자동으로 붙게 했습니다. 수정·삭제·결재도 서버에서 범위를 다시 확인하므로, 폼의 id를 바꿔 다른 팀 데이터를 건드리면 403이 됩니다. 담당자를 이름이 아닌 사용자 id로 묶어 동명이인의 데이터도 섞이지 않습니다.

감사로그는 관리자도 지울 수 없습니다

등록·수정(바뀌기 전과 후)·삭제(지우기 전 내용)·결재·로그인 실패·모든 다운로드를 남깁니다. 각 기록은 바로 앞 기록의 해시를 이어 받고, DB 트리거가 수정과 삭제를 막습니다. 누군가 DB 파일을 직접 고치면 무결성 검증이 몇 번 기록에서 끊겼는지 알려줍니다.

ERP로 보내되, ERP가 멈춰도 영업은 멈추지 않습니다

매출을 저장하는 트랜잭션에서 전송 대기열(Outbox)에 한 줄을 넣고 끝냅니다. 전송은 관리자 화면이나 배치가 따로 합니다. 실패한 건은 원인과 함께 남고 최대 5번까지 다시 보냅니다.

CRM → ERPSAP S/4HANA API_SALES_ORDER_SRV로 판매오더 생성 (CSRF 토큰 발급 → POST). 고객 PO 번호에 CRM 매출번호를 넣어 역방향 대사 키로 씁니다.
파일 방식EAI · SAP PI/PO가 가져가는 JSON 파일. 반쯤 쓴 파일을 읽지 않도록 임시 이름으로 쓴 뒤 이름을 바꿉니다.
ERP → CRMERP의 매출별 누적 입금액을 받아 차액만 입금 등록합니다. 같은 파일을 두 번 올려도 이중 입금되지 않습니다.

SAP 전송은 모의 SAP 서버로 CSRF 토큰·전문·취소(품목 거부사유) 흐름을 테스트했습니다. 실제 SAP 연결은 아직 검증하지 않았습니다.

세금계산서는 확인하고 받습니다

매출마다 세금계산서 이미지, PDF, 전자세금계산서 XML을 붙입니다. 파일 종류는 확장자가 아니라 파일 앞부분(매직 바이트)으로 판별하고, 원본의 SHA-256을 기록합니다. 잘못 올린 증빙은 지우지 않고 사유를 남겨 무효로 돌립니다.

  • CHECK사업자등록번호 검증번호 (가중치 1·3·7·1·3·7·1·3·5)
  • CHECK전자세금계산서 승인번호 24자리 · 같은 승인번호 중복 등록 차단
  • CHECK공급가액 + 세액 = 합계, 매출 금액과 일치, 공급받는자 = 거래처
  • WARN발급 기한(공급한 달의 다음 달 10일)을 넘긴 작성일자
