할인율결재선예
0 ~ 10%팀장한팀장

단계마다 그 역할의 사람이 결재하고, 한 사람은 한 건에서 한 단계만 결재합니다. 출장·휴가 중에는 대결자가 대신 결재하고 기록에 원결재자가 남습니다. 요청 때 정가·제안가·할인율을 고정해 두고, 승인 뒤 금액이나 할인율을 바꾸면 승인이 자동으로 무효가 됩니다.

견적에서 매출까지 금액이 한 줄로 이어집니다

품목 마스터와 거래처 특가(유효기간)를 두고, 견적에서 품목을 고르면 특가, 없으면 정가로 단가가 채워집니다. 영업기회와 연결한 견적은 발송할 때 정가·제안가·할인율을 영업기회에 반영하므로, 결재 없이 할인된 견적이 나갈 수 없습니다.

  • 개정 — 발송한 견적은 고치지 않고 Rev.2로 새 판을 만들고, 이전 판은 '대체됨'으로 남습니다.
  • 매출 전환 — 수락된 견적은 품목별 매출로 한 번만 바뀌고, 매출은 ERP 전송 대기열에 오릅니다.
  • 부가세 — 매출을 공급가액·부가세·합계로 나눕니다. 실적은 공급가액, 채권·입금·ERP·증빙 대조는 합계 기준입니다.

회사가 쓰던 엑셀 양식을 그대로 씁니다

관리자가 회사 파일을 샘플로 올리면 제목과 결재란 아래의 머리글 행을 찾아 열 이름을 시스템 항목에 연결해 둡니다. 그 뒤로 담당자는 ERP에서 뽑은 매출집계표를 고치지 않고 올리면 됩니다.

머리글 찾기글자 칸이 많고 아는 항목 이름과 가장 많이 맞는 행을 머리글로 봅니다.
열 연결상호→거래처명, 품명→품목, 공급가액→금액, 비고→메모. 자동으로 제안하고 관리자가 확인합니다.
값 정리과세코드 01→과세, 병합 셀은 위 값을 이어 쓰고, 합계·소계 행은 건너뜁니다.
같은 검증변환한 뒤에는 표준 업로드와 똑같이 권한·단계 조건·중복을 검사하고, 오류는 원래 엑셀 행 번호로 알립니다.

내려받기도 회사 서식 파일(로고·결재란·테두리)에 데이터만 채워 돌려줍니다. 셀에 적어 둔 {{기간}}, {{합계:공급가액}} 같은 자리를 값으로 바꿉니다.

감사로그는 관리자도 지울 수 없습니다

등록·수정(바뀌기 전과 후)·삭제(지우기 전 내용)·결재·로그인 실패·모든 다운로드를 남깁니다. 각 기록은 바로 앞 기록의 해시를 이어 받고, DB 트리거가 수정과 삭제를 막습니다. 누군가 DB 파일을 직접 고치면 무결성 검증이 몇 번 기록에서 끊겼는지 알려줍니다.

ERP로 보내되, ERP가 멈춰도 영업은 멈추지 않습니다

매출을 저장하는 트랜잭션에서 전송 대기열(Outbox)에 한 줄을 넣고 끝냅니다. 전송은 관리자 화면이나 배치가 따로 합니다. 실패한 건은 원인과 함께 남고 최대 5번까지 다시 보냅니다.

SAPS/4HANA API_SALES_ORDER_SRV로 판매오더 생성 (CSRF 토큰 발급 → POST). 고객 PO 번호에 CRM 매출번호를 넣어 역방향 대사 키로 씁니다.
REST더존·영림원·자체 ERP 앞단 API. 인증(Bearer·Basic·API 키), HMAC 요청 서명, 필드 이름 바꾸기를 설정으로 맞추고, 재전송해도 전표가 두 번 생기지 않게 Idempotency-Key를 보냅니다.
파일EAI · SAP PI/PO가 가져가는 JSON 파일. 반쯤 쓴 파일을 읽지 않도록 임시 이름으로 쓴 뒤 이름을 바꿉니다.
ERP → CRM입금(누적액 → 차액만 반영), 전표번호 회신, 여신한도, 자재 마스터를 API로 받습니다. 같은 값을 다시 보내도 이중 반영되지 않습니다.

SAP와 REST 전송은 모의 ERP 서버로 인증·서명·전문·취소·재전송 흐름을 테스트했습니다. 실제 ERP 연결은 아직 검증하지 않았습니다.

장애가 나도 무엇을 할지 정해 두었습니다

  • 점검 모드 — DB 전환·복구 중에는 조회만 허용하고 저장과 API 쓰기를 503으로 막으며, 워커도 멈춥니다.
  • 백업·복구 — 매일 pg_dump, 복구 명령은 직전에 안전 백업을 한 번 더 뜹니다. 백업 → 변경 → 복구를 테스트로 확인했습니다.
  • 마이그레이션 — 스키마를 처음 버전까지 내렸다 다시 올려도 데이터가 남는지 테스트합니다.
  • 인사 연동 — 피드 인원이 평소의 80% 미만이면 잘린 파일로 보고 멈추고, 마지막 관리자는 비활성화하지 않습니다.
  • 사내 로그인 — OIDC(PKCE·nonce·서명 검증)로 IdP에 직접 붙고, IdP 장애 시 비상 절차를 운영 문서에 적었습니다.
  • 외부 API — 키는 해시로만 저장, 권한 범위·허용 IP·분당 한도(서버끼리 공유), 쓰기 요청은 Idempotency-Key로 한 번만 처리합니다.

경보마다 조치 절차를 연결한 운영 문서(Runbook)와 Docker Compose 구성, SQLite·PostgreSQL로 함께 도는 CI를 두었습니다. 컨테이너 구성은 파일로 작성했고 실제 기동은 아직 확인하지 않았습니다.

세금계산서는 확인하고 받습니다

매출마다 세금계산서 이미지, PDF, 전자세금계산서 XML을 붙입니다. 파일 종류는 확장자가 아니라 파일 앞부분(매직 바이트)으로 판별하고, 원본의 SHA-256을 기록합니다. 잘못 올린 증빙은 지우지 않고 사유를 남겨 무효로 돌립니다.

  • CHECK사업자등록번호 검증번호 (가중치 1·3·7·1·3·7·1·3·5)
  • CHECK전자세금계산서 승인번호 24자리 · 같은 승인번호 중복 등록 차단
  • CHECK공급가액 + 세액 = 합계, 공급가액·세액·합계가 각각 매출과 일치, 공급받는자 = 거래처
  • WARN발급 기한(공급한 달의 다음 달 10일)을 넘긴 작성일자
